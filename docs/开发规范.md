# 开发与验收规范

## 协作

- 日常功能开发以独立分支和 PR 集成为默认流程；提交按可审查、可回滚的逻辑粒度组织，不要求一项任务对应一个提交。
- PR 说明目标、范围、验证结果和已知限制。涉及页面的变更附截图或实际运行结果；涉及法规原文的变更核对来源、条款号与时效性。
- 不提交密钥、敏感图片、运行日志或无关临时文件。规则包中的 `clauses.json` 是条款原文与工程注释的唯一维护位置。

## 检查

```bash
uv run pytest
uv run ruff check .
git diff --check
```

测试与变更风险相称。修改 Schema、规则关联、Pipeline 等核心逻辑时，应覆盖成功与错误边界；文档变更应核对内部引用和代码事实。

## 端到端行为

- Qwen 负责视觉事实、Evidence、限制和 Issue Code 建议；法规名称、原文、关联关系和缺失条件来自本地规则包。
- 未确认的场所属性、法定区域或测量值不得当作已知事实。未知上下文、无有效 Code 或无 Binding 均不应删除 Finding。
- `conditional` 关联同时返回法规与 `missing_conditions`；页面只渲染 `AnalysisResult`，不重新推断法规。
- 发布前用通道堆物、消防设施遮挡、明火或吸烟、电气风险和无明显风险等至少五类真实图片检查上传、模型结果、证据与标注、规则关联和最终展示。
