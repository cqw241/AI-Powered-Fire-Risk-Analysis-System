# 消防风险分析系统 GitHub Flow 开发文档

**依据**：`docs/设计文档.md`（MVP v1.0）  
**适用范围**：本项目从当前设计资料状态到 MVP 验收的开发、评审和合并过程  
**编制日期**：2026-08-23

## 1. 文档定位

- `main` 始终保持可构建、可审查的集成基线；
- 每个 feature 使用独立分支；
- task 和 commit 按开发者认为便于审查和回滚的粒度组织，不强制一一对应；
- worklog 可作为复杂功能的过程记录，但不作为分支创建、提交或合并的强制条件；
- feature 通过 Pull Request（PR）完成评审、检查和合并。



## 2. 系统边界与依赖顺序

### 2.1 目标链路

~~~mermaid
flowchart LR
    A[Gradio 单图上传] --> B[图片解码 / EXIF / 尺寸处理]
    B --> C[Qwen3.8-27B 视觉分析]
    C --> D[Structured Output / Pydantic 校验]
    D --> E[Region、bbox、Evidence、Finding 校验]
    E --> F[Issue Code 白名单过滤]
    F --> G[rule_bindings.json 查询]
    G --> H[clauses.json 回填法规原文]
    H --> I[AnalysisResult 组装]
    I --> J[Gradio 展示图片、风险、法规、整改建议]
~~~

### 2.2 模块与契约

| 阶段 | 目标模块/文件 | 输入 | 输出或不变量 |
| --- | --- | --- | --- |
| 工程入口 | `app.py`、`src/fire_safety/` | 配置和依赖 | `uv run python app.py` 可以启动页面 |
| 图片处理 | `image.py` | JPEG / PNG / WEBP | 解码、EXIF Orientation 修正、尺寸限制；bbox 使用 0–1000 坐标 |
| 模型调用 | `qwen.py`、`prompts/visual_investigator.md` | `PreparedImage`、Issue Code 目录 | 一次图片分析对应一次 Qwen 请求；失败映射为明确状态 |
| 结构化模型 | `schemas.py`、`schemas/*.json` | Qwen JSON | `VisualInvestigation`、`AnalysisResult` 的字段和枚举一致 |
| 视觉结果校验 | `schemas.py` 或校验模块 | Region、Finding、Evidence | 非法 region 删除；无效 bbox 不删除整个 Finding；引用同步清理 |
| 法规规则 | `rules.py`、`data/legal/*.json` | 有效 Issue Code | 只从本地法规数据回填名称、条款号和原文；最多展示 3 条法规 |
| 结果编排 | `pipeline.py` | 图片、视觉结果、规则结果 | 输出 `AnalysisResult`，支持 `completed`、`no_findings`、`image_unusable`、`model_failed`、`invalid_model_output` |
| UI | `ui.py`、`app.py` | `AnalysisResult` | 展示 bbox、Finding、证据、法规、条件缺失信息、整改建议和限制 |
| 测试 | `tests/` | 固定样例、Mock Qwen | Schema、Rule、Pipeline 和至少 5 类真实图片验证通过 |

### 2.3 开发依赖图

~~~text
F01 工程基线
 ├─ F02 图片处理
 ├─ F03 Qwen 与结构化输出
 └─ F04 法规规则
       └─ F05 Pipeline 与最终 UI
              └─ F06 测试与真实图片验收
~~~

F02、F03、F04 可以在 F01 合并后并行开发；F05 必须等待三者合并；F06 以 F05 的完整链路为测试对象。若实际开发中需要调整顺序，在 PR 描述或 issue 中说明新的依赖关系即可。

## 3. GitHub Flow 总流程

### 3.1 分支创建

所有 feature 分支都从最新 `main` 创建，不直接在 `main` 上开发：

~~~bash
git switch main
git pull --ff-only origin main
git switch -c feature/F01-project-bootstrap
~~~

分支名使用 feature 编号和简短英文 slug。需要过程记录时，可复制 `docs/worklogs/_template.md` 建立对应记录；不要求每个分支都创建 worklog。

### 3.2 Task 开发循环

每个 task 应有清晰的完成标准。commit 按逻辑完整、便于审查和回滚的粒度组织，不要求一个 task 只能有一个 commit：

~~~bash
git status
# 实现当前 task
# 运行与当前 task 相关的检查
git diff --check
git add <当前 task 的文件>
git commit -m "feat(F01): 建立 Python 工程基线"
~~~

可以将同一 feature 的相关 task 合并在一个 commit 中，也可以将一个较大的 task 拆成多个 commit；每个 commit 都应描述实际变更，不提交无功能的空提交。

### 3.3 推送和创建 PR

~~~bash
git push -u origin feature/F01-project-bootstrap
~~~

PR 应包含：

- 目标和范围，以及对应的设计文档章节；
- 主要变更和对应的 task；
- 变更文件和关键设计决定；
- 验证命令及结果；
- worklog 链接（如有）；
- 未完成项、已知限制和需要 reviewer 关注的风险。

推荐 PR 标题：

~~~text
feat(F01): 建立工程基线和 Gradio 页面骨架
~~~

### 3.4 Review、CI 和合并

PR 合并前必须满足：

1. PR 的目标、范围和主要变更清楚；
2. 变更没有超出 PR 声明的范围；
3. `uv run pytest`、`uv run ruff check .` 通过（F01 建立命令后适用）；
4. 文档、Prompt、Schema、法规 JSON 的变更已相互对齐；
5. 至少一名 reviewer 通过，且所有阻断意见已处理；
6. 涉及 UI 的变更附截图或本地运行结果；
7. 涉及法规条款的变更完成来源、条款号、原文和时效性复核；
8. `main` 没有未解决冲突，且 PR 基于最新基线。

合并方式由仓库和团队约定决定。合并后删除已合并的远端 feature 分支；是否保留 worklog 由项目需要决定。

## 4. 按开发顺序执行的 Feature 计划

下表是 MVP 的主路线；每个 task 有独立的目标和局部验收，最终以 F06 的端到端验证为准。

| Feature | 分支 | 前置 | 交付目标 |
| --- | --- | --- | --- |
| F01 工程和 Gradio 基线 | `feature/F01-project-bootstrap` | 设计资料 | uv 工程、目标目录和可启动的页面骨架 |
| F02 图片处理 | `feature/F02-image-processing` | F01 | 解码、EXIF、尺寸限制、bbox 转换和绘制 |
| F03 Qwen 结构化分析 | `feature/F03-qwen-structured-analysis` | F01 | Prompt、Qwen Client、Structured Output 和模型错误状态 |
| F04 法规规则 | `feature/F04-legal-rules` | F01 | Issue Code、Binding、Clause 的确定性关联 |
| F05 Pipeline 与最终 UI | `feature/F05-pipeline-ui` | F02、F03、F04 | 端到端结果组装和 Gradio 展示 |
| F06 测试与 MVP 验收 | `feature/F06-test-acceptance` | F05 | 自动化测试、真实图片验证和端到端发布结论 |

### F01：工程和 Gradio 页面骨架

**目标**：建立 Python 3.13、uv、依赖和目标包结构，页面能启动但不承诺分析功能。

| Task | 内容 | 建议 commit | 验收 |
| --- | --- | --- | --- |
| F01-T01 | 创建 `.python-version`、`pyproject.toml`、目标 `src/fire_safety/` 包结构，并声明 Gradio 6.22.0、OpenAI、Pydantic 2、pydantic-settings、Pillow、pytest、ruff。 | `chore(F01): 建立 Python 工程配置` | `uv sync` 成功；依赖版本和 Python 范围符合设计文档。 |
| F01-T02 | 创建 `app.py`、`ui.py` 的最小 Gradio 页面和启动入口，保留单图输入与“开始分析”按钮的位置。 | `feat(F01): 建立 Gradio 页面骨架` | `uv run python app.py` 可启动；页面可打开，尚未接入 Qwen。 |
| F01-T03 | 固定包导入边界、开发命令和配置读取方式；补齐不含密钥的配置说明。 | `docs(F01): 固定工程运行约定` | `uv run ruff check .` 可执行； |

**合并门槛**：页面启动失败时必须在 PR 中说明，不得以“后续 feature 再修”为由合并不可启动基线。

### F02：图片处理和 bbox 绘制

**目标**：把上传文件转换为可供模型和 UI 使用的 `PreparedImage`，并能将 0–1000 bbox 绘制回结果图。

| Task | 内容 | 建议 commit | 验收 |
| --- | --- | --- | --- |
| F02-T01 | 实现 JPEG / PNG / WEBP 解码、EXIF Orientation 修正和尺寸限制；将解码失败映射为 `image_unusable` 所需的异常或结果。 | `feat(F02): 实现图片解码和方向修正` | 三种格式可读；损坏或不支持的图片不会让 UI 崩溃。 |
| F02-T02 | 实现 0–1000 归一化 bbox 到像素坐标的转换，校验顺序、范围和面积。 | `feat(F02): 实现 bbox 坐标校验与转换` | 合法 bbox 转换正确；越界、反转、零面积 bbox 可被识别。 |
| F02-T03 | 在结果图上绘制 bbox 和 Finding 编号；单个 bbox 无效时只忽略该 bbox，不删除整个 Finding。 | `feat(F02): 实现风险区域标注绘制` | 多个 Finding 可区分；图片尺寸变化不会改变标注语义。 |

**合并门槛**：图像处理函数不推算真实米数、净宽、距离或高度；异常边界与设计文档第 13 节一致。

### F03：Qwen Client、Prompt 和 Structured Output

**目标**：完成一次图片对应一次 Qwen 请求，并把模型返回限制为 `VisualInvestigation`。

| Task | 内容 | 建议 commit | 验收 |
| --- | --- | --- | --- |
| F03-T01 | 在 `schemas.py` 实现 `VisualRegion`、`Evidence`、`Finding`、`VisualInvestigation` 等模型，并与 `schemas/visual_investigation.schema.json` 对齐。 | `feat(F03): 建立视觉分析数据模型` | 必填字段、枚举、额外字段限制及 bbox 长度、类型、范围可被程序校验；反转和零面积由后续视觉结果清理。 |
| F03-T02 | 加载 `prompts/visual_investigator.md`，把 `issue_codes.json` 的 code 和简短定义注入 `{{ISSUE_CATALOG}}`；保留视觉事实与法规输出边界。 | `feat(F03): 接入视觉分析 Prompt` | Prompt 不要求模型输出法规名称、条款号、原文或违法结论。 |
| F03-T03 | 实现 Qwen 配置读取、图片发送、Structured Output 请求和错误映射；模型结果无法解析时返回 `invalid_model_output`。 | `feat(F03): 实现 Qwen 结构化调用` | 缺少配置、请求失败、解析失败可区分；一次分析只发送一次模型请求。 |

**合并门槛**：模型只负责视觉理解、Finding 和 Issue Code 建议；法规名称、条款号、原文必须由 F04 程序读取。

### F04：Issue Code 与法规规则

**目标**：加载本地法规规则包，稳定完成白名单过滤、Binding 查询、Clause 回填、排序去重和整改建议。

| Task | 内容 | 建议 commit | 验收 |
| --- | --- | --- | --- |
| F04-T01 | 加载并校验 `clauses.json`、`issue_codes.json`、`rule_bindings.json` 的结构和引用关系。 | `feat(F04): 加载并校验法规规则包` | 当前规则包可加载；未知 clause 或 issue code 能在启动/加载阶段被发现。 |
| F04-T02 | 实现 Issue Code 去重和白名单过滤；无有效 Code 的 Finding 仍保留，法规列表为空。 | `feat(F04): 实现 Issue Code 白名单过滤` | 非法 Code 不进入规则查询；开放 Finding 不丢失；unknown context 不阻止 Finding 输出。 |
| F04-T03 | 实现 Code → Binding → Clause 关联，按 `direct` 优先、`priority` 升序排序，同一 clause 去重，最多返回 3 条，并生成整改建议。 | `feat(F04): 实现确定性法规关联` | `conditional` 继续输出法规及 `missing_conditions`；法规字段全部来自 `clauses.json`；无 Binding 不报错。 |

**合并门槛**：法规关联不由 Qwen 自由生成；unknown context 只影响关联是否为 `conditional` 及其 `missing_conditions`，不得阻止视觉 Finding；任何条款原文修改必须同步 `docs/条款表.md`。

### F05：Pipeline 和最终 Gradio 页面

**目标**：串联图片、Qwen、校验和法规规则，形成完整 `AnalysisResult`，并在 UI 中呈现。

| Task | 内容 | 建议 commit | 验收 |
| --- | --- | --- | --- |
| F05-T01 | 实现 `pipeline.py` 的 `analyze(image)`：图片预处理 → Qwen → 视觉结果校验 → 规则应用。 | `feat(F05): 串联消防风险分析 Pipeline` | Mock Qwen 时可得到稳定的中间和最终结果；unknown context 不会丢弃 Finding。 |
| F05-T02 | 实现 `AnalysisResult` 组装、状态映射和 `schemas/analysis_result.schema.json` 对齐；覆盖无 Finding、图片不可用、模型失败和无效模型输出。 | `feat(F05): 组装 AnalysisResult 状态` | 所有状态值合法；Finding 不因缺少场所用途等 unknown context 被删除；conditional 关联保留法规和 `missing_conditions`。 |
| F05-T03 | 将结果接入 `ui.py`：原图标注、Finding 卡片、证据、风险优先级、法规折叠区、条件缺失信息、整改建议和限制项。 | `feat(F05): 完成 Gradio 分析结果展示` | 无 Finding 显示设计文档规定的提示；有 Finding 时始终展示风险；conditional 法规显示法规正文、条件标签和 `missing_conditions`。 |

**合并门槛**：页面展示层不重新推断法规、不修改 Finding 事实；只渲染 `AnalysisResult`，并确保 unknown context 与 conditional 关联在 UI 中可见。

### F06：自动化测试、真实图片验证和 MVP 验收

**目标**：把设计文档中的契约转成可重复的自动化检查，并留下真实图片验证证据。

| Task | 内容 | 建议 commit | 验收 |
| --- | --- | --- | --- |
| F06-T01 | 编写 Schema 测试：合法输出、bbox 越界/反转、错误 region 引用、重复 Finding ID、空 Evidence。 | `test(F06): 增加 Schema 校验测试` | 失败样例被拒绝或按设计规则清理。 |
| F06-T02 | 编写 Rule 测试：白名单、一个 Code 多条法规、direct/conditional 排序、priority 排序、clause 回填、无 Binding。 | `test(F06): 增加法规规则测试` | 规则结果可重复，最多 3 条且不重复 clause。 |
| F06-T03 | 使用 Mock Qwen 编写 Pipeline 测试，覆盖图片 → Finding → Issue Code → 法规 → `AnalysisResult`。 | `test(F06): 增加端到端 Pipeline 测试` | `uv run pytest` 通过，测试不依赖真实 Qwen Key。 |
| F06-T04 | 用至少五类真实图片做人工端到端验证：通道堆物、消防设施遮挡、明火/吸烟、电气线路与可燃物、无明显风险。记录每类图片的链路结果、Finding、法规关联和限制。 | `test(F06): 完成真实图片端到端验证` | 每类图片都能完成上传 → 模型 → 校验 → 规则 → 结果展示；unknown context 不阻止 Finding；conditional 规则输出法规及 `missing_conditions`。 |
| F06-T05 | 执行发布前检查，补齐 README、设计文档或示例结果中因实现变化产生的最小差异。 | `docs(F06): 完成端到端发布检查` | 端到端验收通过；`pytest`、`ruff` 等适用检查通过。 |

**MVP 合并门槛**：端到端链路必须正确跑通。Git 分支数量、commit 组织方式和 worklog 完整性不是 MVP 功能验收项；它们只作为团队协作参考。

## 6. 发布前最终检查

在 F06 合并前，负责人按以下顺序检查：

1. 可上传 JPEG / PNG / WEBP 图片并触发完整分析；
2. 图片预处理、Qwen Structured Output、视觉校验、Issue Code 过滤、Rule Binding、Clause 回填和 `AnalysisResult` 组装均成功执行；
3. Finding 有可见证据时可展示，unknown context 不会阻止 Finding 输出；
4. `direct` 和 `conditional` 规则均按顺序返回；`conditional` 始终同时返回法规信息与 `missing_conditions`；
5. 无有效 Issue Code 或无 Rule Binding 的 Finding 仍保留，法规为空但页面不丢失风险；
6. UI 能展示标注图片、Finding、证据、优先级、法规、缺失条件、整改建议和限制；
7. 图片不可用、模型失败、结构化输出无效等错误状态可区分且不会导致页面崩溃；
8. 自动化测试和适用 lint 检查通过，并至少完成五类真实图片的端到端验证。
